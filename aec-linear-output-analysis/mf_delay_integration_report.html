2. 核心概念：Lookahead

2.1 什么是 Lookahead

Binary 延时估计器内部维护一个 near_history FIFO。每帧不是用当前 near spectrum 做比较，而是取 near_history[lookahead]（即 lookahead 帧之前的 near）做比较。

物理含义：不是"用未来的 near"，而是"延迟使用过去的 near，让 far_history 有更多时间积累"。代价是估计结果延迟 L 帧出来。

2.2 代码体现

// delay_estimator.c — Evz_ProcessBinarySpectrum()
if (self->near_history_size > 1) {
    memmove(&self->binary_near_history[1], &self->binary_near_history[0], ...);
    self->binary_near_history[0] = binary_near_spectrum;  // 存入当前
    binary_near_spectrum = self->binary_near_history[self->lookahead];  // 取旧的
}
// 然后用这个"旧 near" 和 far_history 做 BitCountComparison

2.3 为什么 Binary 输出要减去 Lookahead

时刻 T，真实回声延时 = D blocks，lookahead = L near_history: [N_T, N_T-1, ..., N_T-L] ↑ 实际用 N_(T-L) 做比较 far_history: [F_T, F_T-1, ..., F_T-L-D, ...] [0] [1] [L+D] N_(T-L) 的回声来自 F_(T-L-D) F_(T-L-D) 在 far_history 中位置 = T - (T-L-D) = L + D Binary 搜索结果: last_delay = L + D 真实残余延时: delay = last_delay - L = D 结论: 减 lookahead 是去掉 near 被延迟使用带来的虚假偏移

2.4 SoftReset 如何改变 Lookahead

int Evz_SoftResetBinaryDelayEstimator(self, delay_shift) {
    old = self->lookahead;
    self->lookahead -= delay_shift;
    clamp to [0, near_history_size-1];
    return old - self->lookahead;  // 实际移动量
}
修正方向moved_elementslookahead 变化原因
Far 回退（负修正）-N+N（增加）far 坐标后退，near 也要后退保持对齐
Far 前移（正修正）+N-N（减少）far 坐标前进，near 跟着前进
SoftReset Far 侧 (delay_shift = -3，far 回退): 修正前: far_history = [F5, F4, F3, F2, F1, F0, ...] memmove: 丢掉 F5/F4/F3，从 F2 开始 修正后: far_history = [F2, F1, F0, 0, 0, 0, ...] 此时 far[0] = F2（3帧前的），near 也要用 3帧前的 → lookahead += 3，取 near_history[3] = N_(T-3) → N_(T-3) 和 F2 是同一时刻，对齐关系恢复 ✓

2.5 关键等式

lookahead = -signal_delay_correction（初始 lookahead=0 时成立）
因此 mf_abs - lookahead = mf_abs - |已修正量| = 剩余需修正量

3. MF 集成方案演进与问题

3.1 方案A（失败）：MF残余 + 减lookahead = 双重减法

代码：last_delay = mf_abs - |signal_delay_correction|，然后 delay = last_delay - lookahead
问题：等于减了两次已修正量（correction ≈ lookahead），得出极小或负值触发反向修正
日志表现：last_delay=6 delay=-104 corr=+105 然后 last_delay=111 delay=106 corr=-105 交替震荡

3.2 方案B（失败）：方案A + Snapshot 防帧内变化

思路：帧开始快照 signal_delay_correction，帧内两次 sub-frame 用同一值
问题：帧内不震荡了，但跨帧仍然震荡（帧N修正改变correction，帧N+1 snapshot不同）
根因：本质仍是双重减法

3.3 最终方案（两种等价模式）

RAW 模式（#define MF_DELAY_RAW_ABSOLUTE）：
last_delay = mf_abs，delay = last_delay - lookahead
只减一次（靠 lookahead）

Residual 模式（默认）：
last_delay = mf_abs - |snapshot|，delay = last_delay（MF不减lookahead）
只减一次（靠 snapshot/correction）

数学等价：两者最终 delay = mf_abs - 已修正量，只是"已修正量"的来源不同（lookahead vs signal_delay_correction）。

4. 为什么每次修正后要 SoftReset Buffer

目的：保持 Binary 延时估计器的坐标系与 far_buf 物理状态一致。

当 MoveFarReadPtr 移动了 far_buf 读指针后，Binary 内部的 far_history 如果不做对应移动，下一帧搜索会在错误的位置找匹配，导致延时估计跳变。

操作SoftReset Far 侧SoftReset Near 侧效果
Far 回退 N blocksmemmove far_history 右移 N，前面 pad 0lookahead += Nfar/near 坐标同步后退
Far 前移 N blocksmemmove far_history 左移 N，后面 pad 0lookahead -= Nfar/near 坐标同步前进

5. SoftReset 详解：为什么修正后必须同步 Binary 内部状态

5.1 调用时机

// aec_core.c — EvzAec_ProcessFrames
int move_elements = SignalBasedDelayCorrection(aec);
int moved_elements = MoveFarReadPtrWithoutSystemDelayUpdate(aec, move_elements);
// ↓↓↓ 修正 far_buf 后，必须同步 Binary 内部状态 ↓↓↓
Evz_SoftResetDelayEstimator(aec->delay_estimator, moved_elements);
Evz_SoftResetDelayEstimatorFarend(aec->delay_estimator_farend, moved_elements);
aec->signal_delay_correction += moved_elements;

5.2 为什么需要执行这两个函数

核心问题：MoveFarReadPtr 改变了 far_buf 的物理读取位置。但 Binary 延时估计器内部有自己独立的 far_history 和 near_history，它们的坐标系如果不做对应调整，下一帧搜索会在错误位置匹配，产生延时估计跳变。

5.3 Evz_SoftResetDelayEstimatorFarend — 调整 far 侧坐标

函数调用链：Evz_SoftResetDelayEstimatorFarend → Evz_SoftResetBinaryDelayEstimatorFarend

void Evz_SoftResetBinaryDelayEstimatorFarend(self, delay_shift) {
    // delay_shift = moved_elements（正=前移，负=回退）
    if (delay_shift > 0) {
        // Far 前移：丢掉最老的 delay_shift 个，最新的不变
        dest_index = delay_shift;  // 右移
        memmove(&far_history[dest_index], &far_history[0], shift_size);
        memset(&far_history[0], 0, delay_shift);  // 前面补零
    } else if (delay_shift < 0) {
        // Far 回退：丢掉最新的 |shift| 个，从老的开始
        src_index = |delay_shift|;
        memmove(&far_history[0], &far_history[src_index], shift_size);
        memset(&far_history[shift_size], 0, |delay_shift|);  // 后面补零
    }
}
场景：moved_elements = -47（far_buf 回退 47 blocks） 修正前 far_history（Binary 内部）: [F_now, F_now-1, ..., F_now-46, F_now-47, ..., F_now-499] [0] [1] [46] [47] [499] MoveFarReadPtr 把 far_buf 读指针后退了 47 → 自适应滤波器现在从 F_now-47 开始读 但 far_history[0] 还是 F_now → 坐标不一致！ SoftResetFarend(delay_shift=-47): src_index = 47 memmove: far_history[0..452] = far_history[47..499] memset: far_history[453..499] = 0 修正后 far_history: [F_now-47, F_now-48, ..., F_now-499, 0, 0, ..., 0] [0] [1] [452] [453] [499] 现在 far_history[0] = F_now-47，和 far_buf 读指针对齐 ✓ Binary 下次搜索在正确坐标系下进行

5.4 Evz_SoftResetDelayEstimator — 调整 near 侧坐标 (lookahead)

函数调用链：Evz_SoftResetDelayEstimator → Evz_SoftResetBinaryDelayEstimator

int Evz_SoftResetBinaryDelayEstimator(self, delay_shift) {
    int old_lookahead = self->lookahead;
    self->lookahead -= delay_shift;
    clamp to [0, near_history_size - 1];
    return old_lookahead - self->lookahead;  // 实际调整量
}
为什么 near 侧也要调整：far_history 被移动后，如果 near 还用"当前帧"做比较，时间对应关系就错了。通过调整 lookahead，让 Binary 取 near_history 中对应时刻的 near spectrum，保持 far/near 时间对齐。
场景：moved_elements = -47（far 回退），lookahead: 0 → 47 修正前： far_history[0] = F_now, near 用的是 N_now (lookahead=0) → F_now 和 N_now 是同一时刻 ✓ 修正后（far_history 被移动）: far_history[0] = F_now-47, 如果 near 还用 N_now (lookahead=0) → F_now-47 和 N_now 差了 47 帧！✗ 调整 lookahead = 47: near 改用 near_history[47] = N_now-47 → F_now-47 和 N_now-47 是同一时刻 ✓ 对齐恢复

5.5 如果不执行 SoftReset 会怎样

不执行的后果表现
不执行 SoftResetFarendfar_history 坐标和 far_buf 物理位置不一致，Binary 搜索到的 last_delay 会突变（跳到错误位置），可能触发不必要的二次修正或来回震荡
不执行 SoftResetDelayEstimatorlookahead 不变，near/far 时间错位，Binary 输出的 last_delay 包含了不正确的偏移，减去 lookahead 后得到错误残余值
两者都不执行Binary 完全失去跟踪能力，持续输出错误延时，SignalBasedDelayCorrection 反复修正导致系统不稳定

5.6 对 MF 的影响

MF 延时估计器有自己独立的 far/near 数据流（通过 mf_far_fifo），不受 Binary 的 SoftReset 影响。MF 始终输出绝对延时。但 SoftReset 改变了 lookahead 值，在 RAW 模式下 delay = mf_abs - lookahead，lookahead 的变化正好反映了系统已修正的量，使 MF 输出能正确转换为残余延时。

6.2 last_delay 在不同状态下的值

一个常见疑问：之前说 last_delay = L + D，SoftReset 后又变成 last_delay = D，是否矛盾？

不矛盾。两者是同一公式在不同 far_history 坐标系下的正确结果。
关键区别：far_history 的"起点时间"不同了。SoftReset memmove 把坐标原点从 T 移到了 T-3。
delay = last_delay - lookahead 始终输出正确的残余延时。

场景 1：初始状态，无修正，lookahead=L

far_history 没被移动过，[0]=F_T (最新) near 用的是 N_T-L (lookahead=L) N_T-L 的回声来自 F_(T-L-D) F_(T-L-D) 在 far_history 中位置 = T - (T-L-D) = L+D last_delay = L+D delay = last_delay - lookahead = (L+D) - L = D ← 真实延时（全部）

场景 2：SoftReset 后，far_history 移动了 3 位，lookahead=3

far_history 被 memmove 过，[0]=F_T-3（不再是最新，坐标原点=T-3） near 用的是 N_T-3 (lookahead=3) N_T-3 的回声来自 F_(T-3-D) F_(T-3-D) 在新 far_history 中位置: 新起点时间 = T-3 F_(T-3-D) 相对起点偏移 = (T-3) - (T-3-D) = D last_delay = D delay = last_delay - lookahead = D - 3 ← 残余延时（减去已修正的3）

对比总结

状态far_history[0]起点near 使用last_delaylookaheaddelay含义
初始(未修正)F_TN_T-LL+DLD全部延时
修正3后F_T-3N_T-3D3D-3剩余延时

last_delay 的绝对值随 SoftReset 变化（坐标系变了），lookahead 也随之变化，两者的差 delay = last_delay - lookahead 始终给出正确的"还需修正多少"。

6.3 SoftReset 数据变化详解

SoftResetFarend (delay_shift=-85, far 回退)

binary_far_history 修改前: [0]=F_T [1]=F_T-1 ... [84]=F_T-84 [85]=F_T-85 ... [499]=F_T-499 操作: memmove([0], [85], 415) + memset([415], 0, 85) binary_far_history 修改后: [0]=F_T-85 [1]=F_T-86 ... [414]=F_T-499 [415..499]=0 效果: 丢掉最新85帧，[0]对齐到 F_T-85 (和 far_buf 物理回退一致)

SoftResetEstimator (delay_shift=-85)

binary_near_history 数据不变: [0]=N_T [1]=N_T-1 ... [85]=N_T-85 ... [500]=N_T-500 lookahead: 0 → 85 效果: 下次比较取 near_history[85]=N_T-85 与 far_history[0]=F_T-85 时间对齐 ✓

为什么 far 必须 memmove 而 near 只改 lookahead

far_history：BitCountComparison 遍历 far_history[0..499] 全部位置做比较，没有"从某offset开始"的参数。如果不 memmove，位置 0 的数据仍是 F_T，搜索结果在错误坐标。

near_history：ProcessBinarySpectrum 中通过 binary_near_spectrum = near_history[lookahead] 取值，只用一个元素。改 lookahead 就等于改了"用哪个 near"，不需要动数组。

7. MF/Binary 切换安全性

当 MF confidence 波动导致帧间 MF↔Binary 切换时：

  • Binary 的 last_delay 是在 SoftReset 后坐标系下搜索的结果，减去 lookahead 得到真实残余
  • MF 的 mf_abs - lookahead 也得到真实残余
  • 两者最终 delay 值相近（都是真实残余），切换不会引起跳变

8. 调试中遇到的关键问题总结

#问题根因解决

9. 当前代码结构（宏控制）

#define AEC_ENHANCED_DELAY_EST          // 总开关
// #define MF_DELAY_RAW_ABSOLUTE        // 取消注释=RAW模式，注释=Residual模式

// aec_core.c — SignalBasedDelayCorrection
#ifdef AEC_ENHANCED_DELAY_EST
  if (mf_fused_delay_blocks > 0 && mf_fused_confidence >= 0.8f) {
    #ifdef MF_DELAY_RAW_ABSOLUTE
      last_delay = mf_fused_delay_blocks;           // 直接用绝对值
    #else
      last_delay = mf_fused_delay_blocks - |snapshot|; // 减已修正量
      if (last_delay < 0) last_delay = 0;
    #endif
    mf_is_source = 1;
  } else {
    last_delay = Evz_last_delay(delay_estimator);   // Binary fallback
  }

  #ifdef MF_DELAY_RAW_ABSOLUTE
    delay = last_delay - lookahead;                 // 统一减 lookahead
  #else
    delay = mf_is_source ? last_delay : (last_delay - lookahead);
  #endif
#endif
